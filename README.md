# MINIX 3.4.0 — amd64 UEFI branch

This repository is a MINIX 3.4.0 with UEFI
boot support and an x86_64 (amd64) port.

## Build an amd64 UEFI installation ISO

The cross-build environment is Ubuntu 26.04.

```sh
./build.sh -U -u -m amd64 -O ../build release
./build.sh -U -u -m amd64 -O ../build iso-image
```

The resulting image is:

```
../build/releasedir/images/Minix-3.4.0-x86_64-install.iso
```

The amd64 `iso-image` target invokes
`releasetools/x86_64_uefi_cdimage.sh`. It builds a FAT32 EFI El Torito
boot image containing `EFI/BOOT/BOOTX64.EFI`, and an ISO9660 filesystem
containing the amd64 kernel, boot modules, boot menu and release sets.
The boot menu uses the 64-bit UEFI loader and Multiboot2 entry point; it
is not the legacy 32-bit BIOS image generated by
`releasetools/x86_cdimage.sh`.

The ISO build downloads the current source snapshot from
`eclairdosesleekman/pkgsrc` and adds it as the `pkgsrc.tgz` release set.
At ISO build time, the helper reads the repository's default branch from the
GitHub API, resolves its current tip to an immutable commit, and downloads
that commit's codeload archive. The installer extracts this set into
`/usr/pkgsrc`, so the pkgsrc sources are available after installation
without curl, wget, or git on MINIX.

For a reproducible build, set `PKGSRC_COMMIT=<40-character-commit-sha>`.
To select a branch other than the repository default, set
`PKGSRC_BRANCH=<branch-name>`. To use a pre-fetched codeload archive, set
`PKGSRC_ARCHIVE=/path/to/pkgsrc.tar.gz`. The downloaded archive is cached
under the build work directory using its resolved commit SHA. The first ISO
build needs network access on the Ubuntu build host.

For direct invocation after a release build, run
`OBJ=../build bash releasetools/x86_64_uefi_cdimage.sh`. Set
`CREATE_IMAGE_ONLY=0` to have the helper run the release build before
packaging. Paths and image settings can be overridden with `OBJ`,
`DESTDIR`, `RELEASEDIR`, `SETS_DIR`, `CROSS_TOOLS`, `WORK_DIR`,
`IMG`, `XORRISO`, and `EFIMB`.

## Installing MINIX to a UEFI disk

The amd64 UEFI ISO starts the guided installer on the primary console.
From a root shell, the same installer can be started manually:

```sh
/usr/sbin/minix-install
```

The guided flow follows the 32-bit MINIX setup procedure, adapted to the
amd64 UEFI/GPT boot layout:

1. Select a keyboard map.
2. Choose automatic partition creation or expert mode with an existing GPT.
3. In automatic mode, choose the size of a separate `/home` partition.
4. Choose a full installation or, when an existing MFS `/home` is found,
   reinstall while preserving its contents.
5. Select the MFS filesystem block size.
6. Install the available release sets, amd64 kernel and boot modules, and
   create the target device nodes.
7. Configure networking interactively and install `pkgin` when its package
   archives are present on the installation media.

Release archives are read from `/usr/amd64/binary/sets`. The installer
also extracts the bundled pkgsrc sources into `/usr/pkgsrc`; after booting
the installed system, the bootstrap script is available at
`/usr/pkgsrc/bootstrap/bootstrap`.

Automatic mode creates a GPT containing a 64 MiB FAT32 EFI System Partition
(`c0d0p0`), a 128 MiB MFS root (`c0d0p1`), an optional MFS `/home`
(`c0d0p2`), and an MFS `/usr` using the remaining space. If `/home`
is disabled, `/usr` is `c0d0p2`. Expert mode reuses a previously
prepared GPT with the same partition device names. The root must remain
partition 1 (device `/dev/c0d0p1`) because the installed UEFI boot menu
currently supplies `rootdevname=c0d0p1`.

**Destructive operation:** automatic mode erases the selected disk's
partition table and all partitions. Expert mode overwrites the EFI, root,
and `/usr` filesystems; `/home` is reformatted only for a full
installation. The installer checks that the target is not mounted and
requires an exact typed confirmation before writing to the disk. In the
reinstall path, an existing MFS `/home` is preserved.

The amd64 installer is experimental. Test the ISO and both partitioning
modes in a VM before installing on physical hardware.

## MXV (MINIX eXtended Virtualizarion)

MXV is MINIX 3 native hypervisor.
Taking advantage of the microkernel design of MINIX3, MXV is designed to make many functions as possible work on the userland side.
Unlike Linux's KVM and NetBSD's NVMM, MXV does not use QEMU and acts as a hypervisor on its own, like FreeBSD's bhyve.
The design of the microkernel MINIX 3 does not suit the hypervisor that uses QEMU like NVMM, and bhyve developed on the premise of monolithic kernel is not suitable for MINIX 3, so MXV was decided to develop a native hypervisor.
The development of the MXV is now in phase 1.
